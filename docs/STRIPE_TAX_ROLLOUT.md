# RetainAI Stripe Tax: prepared, disabled

This change does not activate Stripe Tax, register a tax account, change product classification, change prices, or migrate existing subscribers. `RETAINAI_STRIPE_AUTOMATIC_TAX` is absent/false by default. Deploying this code alone keeps new sessions on the existing tax-off contract. The pinned Stripe SDK/API and card payment-method configuration are unchanged.

## Read-only server preflight

Use the intended environment's existing `STRIPE_SECRET_KEY` and `STRIPE_PRICE_ID`; do not paste a key into command arguments or logs:

```sh
python backend/stripe_tax_preflight.py --mode live --expected-account acct_1KnWUNLKkR3ZKFQy --expected-product prod_STCTlo7l9X3qEn
```

The report verifies account, price/product and mode; summarizes tax settings, registration country/status, and subscription counts for the configured price. It requires the Canadian federal standard registration to be active in the matching mode with an effective start date and no elapsed expiry; provincial-only, simplified, scheduled or incomplete registration data cannot pass. Tax-code presence is checked separately from the owner’s legal classification approval. It prints no customer emails, addresses, registration numbers, bank details, API keys or customer IDs. All provider methods are retrieve/list. Exit 0 means the limited technical checks passed, 2 means a readiness check failed, and 1 means the read could not be completed. This is not approval to activate tax: classification, fees, legacy-session inventory, sandbox evidence and existing-subscription decisions remain explicit gates. The utility has only been tested with mocked providers until an operator runs it in the intended environment.

## Checkout guarantees and support handling

- The dedicated `billing_checkout_attempts.json` ledger is locked and atomically written before Stripe creation. It freezes exact request parameters, policy version, account generation, and idempotency key. Same-policy retries reuse those exact bytes semantically, even if trial/cancel/referral inputs change. Concurrent callers select the same attempt.
- A policy/price mismatch while pending or open blocks another checkout. An unknown result at or beyond 24 hours blocks retries because Stripe can prune idempotency keys. Provider retrieval failures also block. Restoring the original flag/price permits only a safe original-policy retry within the window; after that, reconcile in Stripe before any operator repair.
- A complete session without a resolved subscription blocks a new checkout. Existing active/recoverable subscriptions are returned; verified expired sessions or completed sessions with canceled/incomplete-expired subscriptions permit the next generation.
- Created/retrieved sessions are checked for mode, identity, customer/email binding, tax setting and trusted Stripe Checkout URL before a URL is returned. An unexpected tax response preserves the known session ID and stops for support.
- New customers use Checkout's minimum billing location collection for automatic tax. Returning customers collect fresh billing address and persist it through `customer_update.address=auto`. A saved shipping address takes precedence in Stripe; the application stops with a support message instead of silently deleting it or using the wrong location. No tax-ID collection is added.
- Account deletion purges the ledger under the same lock; account export includes only policy, generation, creation time and session ID, not the frozen request or idempotency key. Late responses cannot restore a deleted/recreated account. The helper refreshes user state after provider I/O and writes only billing fields, preserving administrative suspension and current profile edits.
- The application's pre-existing whole-users-map storage API still has a general load/save concurrency window. This patch avoids holding the pre-provider snapshot but does not redesign storage transactions across all account routes.

## Rollback

Keep this code and the ledger when reverting the flag. A true-to-false toggle intentionally blocks pending/open tax-enabled sessions until reviewed; it does not invalidate them remotely or change already-created subscriptions. A code rollback to the old checkout helper would bypass these guards and is not a safe tax rollback. Stop new checkouts if necessary, reconcile pending sessions/subscriptions, and preserve receipts before any separately reviewed repair.
